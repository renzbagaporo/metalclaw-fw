# sim7080g

A SIMCom SIM7080G LTE-M/NB-IoT modem on UART, with its PWRKEY. The harness
answers the AT commands of the SIM7070/SIM7080/SIM7090 Series AT Command
Manual V1.07 that Zephyr's `simcom,sim7080` offload driver and TinyGSM's
SIM7080 client send, so the board under test can boot the modem, attach,
bring up the data bearer, resolve names, open TCP and UDP sockets, read
GNSS fixes, list and send SMS and download over FTP, against the package's
[fake network](README.md#the-fake-network).

`sim7080g.c` holds the descriptors, the config and the model's own
commands and URCs; `sim7080g_sockets.c` is DNS and the `CA*` commands. The
engine, the standard commands, SMS and the network are the package's
([README](README.md)). The model has all four parts: modem, network,
GNSS and SMS, so its properties and regions are every one the README
lists.

## Attaching

The UART binding advertises the module's fixed rate, 115200 baud 8N1. On
fixture 1 the crossed pair is GP0/GP1 and the DUT's GP6 drives the
harness's GP6:

```python
import metalclaw
modem = metalclaw.attach("sim7080g", "modem", uart=(0, 1), pwrkey=6)
modem.write_region("hosts", 0, b"vsh.pp.ua=192.0.2.80\nbroker.hivemq.com=192.0.2.18\n\0")
modem.write_region("file", 0, open("test_1k.bin", "rb").read())
modem.set(file_length=1024, latitude=31221946, longitude=121355565, fix=True, satellites=9)
modem.powered, modem.pdp, modem.connections, modem.bytes_down
modem.read_region("request", 0, 96)
modem.write_region("mqtt_inject", 0, b"GsmClientTest/led\n1\0")
modem.set(mqtt_send=True)
modem.reset()
modem.detach()
```

`pdp` is PDP context 0, `connections` counts successful `CAOPEN`s,
`registration` is the `+CEREG` stat, `boot_ms` defaults to 3000 and
`power_cycles` counts `RDY`s sent.

## Power and timing

| from | event | to |
| --- | --- | --- |
| off | PWRKEY low for 500 ms (Ton) | booting |
| booting or on | PWRKEY low for 1200 ms (Toff) | `NORMAL POWER DOWN`, off |
| booting | `boot_ms` later | `RDY`, `+CFUN: 1`, `+CPIN: READY` (or `NOT INSERTED`, `SIM PIN`), `SMS Ready`; on |
| on | `AT+CPOWD=1` | `NORMAL POWER DOWN`, off (`AT+CPOWD=0`: off, silent) |
| on | `AT+CFUN=1,1`, `AT+CFUN=6`, `AT+CREBOOT` | `OK`, booting |

Zephyr's 1.5 s pulse therefore boots an off modem (`RDY` 3.5 s after the
press starts) and powers down an on one 1.2 s in. The baud rate survives a
boot, as `AT+IPR` is saved by the module.

Answers trail commands only where a driver needs it: `+APP PDP`,
`+CDNSGIP`, `+CNTP` and `+FTPGET: 1,1` come 110 ms after the command (at
least 100 ms after its `OK` has left), and the `OK` of a `CASEND` data
phase 5 ms after its last byte. Everything else is answered from `on_rx`.
One `+CADATAIND` and one `+CASTATE` wait per connection, and a
connection's pending URCs go when it is closed or its cid is opened again.
Input waits while the output FIFO has less than 256 bytes free, room for
the longest `AT+CAOPEN?` list; a URC waits for 112, room for a `+CDNSGIP`
with a 64-character host.

`+CGNSINF` has the 18 fields of the manual's table 8-1. GNSS off it is
`0` and seventeen empty fields. On without a fix: `1,0,<utc>,,,,,,0,,,,,,<satellites>,,,`.
With a fix: run 1, fix 1, UTC `yyyyMMddhhmmss.000`, latitude and longitude
with six decimals, altitude in metres with three, speed in km/h with two,
course with one, fix mode 1, HDOP, PDOP and VDOP all equal to `hdop` with
one decimal, satellites in view, and HPA and VPA of five times HDOP in
metres.

## Sockets

TLS asked for with `CASSLCFG`/`CSSLCFG` is accepted and the same plaintext
services answer. `+CADATAIND: <cid>` is sent when a socket's data goes
from none to some, and again after a `CARECV` that leaves data behind. A
server close is reported as `+CASTATE: <cid>,0` only once the DUT has read
every byte; the socket then answers `CASTATE?` with 0 until `CACLOSE`.
Losing registration, CFUN 0 or 4, `CGATT=0` or `CNACT=0,0` ends every
connection: `+APP PDP: 0,DEACTIVE` and a `+CASTATE: <cid>,0` per open
socket, pending data discarded.

A `CARECV` answer is at most what the output FIFO can take (about 680
bytes). When it leaves data behind, it ends so that the next answer does
not start with CR or LF, which would stall the Zephyr driver; it keeps the
asked length only when every byte after the first is CR or LF.

## The Zephyr driver this is built against

Zephyr v4.4.0, the offload driver `drivers/modem/simcom/sim7080`
(`CONFIG_MODEM_SIM7080`), on the interrupt-driven UART. Its init pulses
`mdm-power-gpios` for 1.5 s and waits 5 s for `RDY` and then for
`+CPIN: READY`; `NORMAL POWER DOWN` instead tells it the modem was already
on, and it pulses again. Then `ATE0`; `CGMI`, `CGMM` (compared exactly
with `SIMCOM_SIM7080`), `CGMR`, `CGSN`, `CIMI`, `CCID`; `CNMP`, `CMNB`,
`CBANDCFG`; `CSQ` until valid; `CGATT?` until attached; `CEREG?` until
stat 1 or 5; `CNCFG=0,0`; `CNACT=0,1` and a wait for `+APP PDP: 0,ACTIVE`.
`power_off` pulses PWRKEY and waits for `NORMAL POWER DOWN`; it never sends
`CPOWD`.

The quirks the model accommodates:

- `+CFUN: 1` comes before `+CPIN: READY` at boot: during the identity
  queries any line the driver does not expect overwrites a stored field.
- `+APP PDP` trails the `CNACT` `OK` by 110 ms: the driver resets its
  semaphore after the `OK`, and a URC in the same burst is lost (120 s
  timeout).
- The `CASEND` data phase's `OK` trails the data by 5 ms for the same
  reason.
- `CDNSGIP` never answers `ERROR`: the driver waits 210 s for the URC.
- `CASEND=<cid>` reports 1460, which fits the driver's four-digit length.
- `+CARECV` is never 0 and never starts its data with CR or LF while it
  can avoid it; with nothing buffered the answer is an error.
- `+CADATAIND` is sent again after a partial read, as the driver zeroes its
  pending count after every `CARECV`.
- `+CGNSINF` has exactly six, three, two and one decimals where the driver
  scales by fixed powers of ten.
- `+CMGL` separators are exactly CR LF.

The driver looks `+CADATAIND` and `+CASTATE` up by file descriptor rather
than connection ID, so receive works only with POSIX device I/O off; that
is the DUT image's concern, not the model's.

## TinyGSM

TinyGSM 0.12's `TinyGsmClientSIM7080` works against the model too: its AT
probe sees the echo, sends `ATE0` and finds echo really off; `AT+CARECV?`,
which the manual does not list, answers one line per socket with data;
`AT+CSSLCFG="ctxindex",0` gets its `+CSSLCFG:` line; every `print()` is
its own `CASEND`, and the LF after each command's CR is not taken as
payload; `+CAOPEN` comes before `OK`. TinyGSM parses a 21-field
`+CGNSINF`; the model sends the SIM7080's 18, so TinyGSM reads `usat` as
-9999 and waits out a few timeouts, as it does with a real module.

## Not modelled

PPP, CMUX and `ATD` (Zephyr's `modem_cellular` driver), `AT+CASERVER`,
transparent mode (`CASWITCH`), `recv_mode` 1 and `+CAURC`, `CAACK`,
`CASRIP`, the TLS handshake and certificates, the HTTP(S), MQTT(S), ping
and file-system application commands (`SH*`, `SM*`, `HTTPTOFS`, ...),
XTRA, `AT+CUSD`, calls, incoming SMS and `+CMTI`, text-mode `CMGL`,
`+CREG` location fields (`n` 2 and 4 report like 1), PDP contexts 1 to 3,
FTP upload and every FTP command beyond the download, autobauding
(`AT+IPR=0`), flow control, PSM and eDRX, sleep and DTR, command
concatenation with `;`, and the `AUTO_SAVE` of anything but the baud rate.
The clock in `time` does not run, `+CNTP` does not set it, and the RF
sharing between GNSS and LTE is not modelled: GNSS works with the bearer
up.

## The DUT image

`test/dut/sim7080g/rp2.overlay` puts `uart0` on GP0/GP1 at
`current-speed` 115200, removes the console from it, and hangs a
`simcom,sim7080` node aliased `modem` under it with `mdm-power-gpios` on
GP6, active low. The node is `zephyr,deferred-init`: Zephyr's offload
driver boots the part, reads its identity and activates PDP inside its
init, retrying for about 30 s without a modem, and the rig flashes and
pings the DUT before a case attaches the model. `MODEM INIT` runs that
init and then brings the offloaded interface up, which the net stack's own
bring-up at boot skipped because the device was not ready. A GPIO hog
drives GP6 released from boot, since the driver only configures the pin in
its deferred init and an RP2350 pad resets with its pull-down on.
`test/dut/sim7080g/rp2.conf` turns on the serial driver, interrupt driven,
`CONFIG_MODEM_SIM7080` with sockets and no native stack, five file
descriptors, and no POSIX device IO: the driver looks sockets up by file
descriptor where it means the modem's connection id, so the first
descriptor must be 0.

The DUT commands are the socket API (`DNS`, `TCP`, `UDP`, `HTTP`, `SOCK`)
and the driver's vendor API under `MODEM` (`INIT`, `STATE`, `INFO`,
`POWER`, `NET`, `GNSS`, `SMS`, `BATTERY`, `CELL`, `TIME`, `FTP`); the
reference is `test/rig/dut/README.md`.

```sh
just build-dut cellular/sim7080g
METALCLAW_HARNESS_SERIAL=<serial> METALCLAW_ARM_TOOLCHAIN_DIR=<dir> \
METALCLAW_DUT_DEVICE=cellular/sim7080g just test hardware
```

## Tests

`test/cases/test_sim7080g.py` runs on the `cellular/sim7080g` image. It
attaches the model at `uart=(0, 1)` and `pwrkey=6`, writes three names
into `hosts` and a printable 1 KiB `file`, resets the DUT and runs
`MODEM INIT`, then checks: the driver powered the part through PWRKEY (one
boot, PDP active, no unknown command); the identity strings as the driver
stores them; DNS for every `hosts` name, a literal, and an unknown name
(which the driver reports as `0.0.0.0`); TCP echo of 1 to 1000 bytes in
256-byte chunks, three rounds each, intact by CRC, with the model's
connection and byte counters and no drops; binary bytes through the echo;
UDP echo up to 256 bytes; an HTTP GET of the file intact and the request
line in `request`, a 404 when `file_length` is 0, and a refused port;
losing registration drops PDP and closes an open socket while the driver
stays in NETWORKING; four GNSS fixes converted exactly as the driver scales
them, including the sign it loses between -1 and 0; three 7-bit SMS read
field for field, one deleted; battery; the serving cell; local time with
the driver's year quirk; an FTP get intact; power off and on through
PWRKEY; and a DUT reset that makes the driver's init turn the running
modem off and on again.
