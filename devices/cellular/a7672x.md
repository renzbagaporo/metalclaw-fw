# a7672x

A SIMCom A7672X (A76XX series, LTE Cat-1) modem on UART, with its PWRKEY.
The harness answers the AT commands of the A76XX Series AT Command Manual
V2.04 and the A76XX Series TCPIP AT Command Manual V1.00 that TinyGSM's
A7672X client and Zephyr's `modem_cellular` driver (`simcom,a76xx`) send,
so the board under test can boot the modem, register, bring up context 1,
open TCP links and SSL sessions in buffer mode, multiplex the UART with
CMUX and dial PPP, look up its base-station location, sync NTP and send
SMS, against the package's [fake network](README.md#the-fake-network).

`a7672x.c` holds the descriptors, the config and the model's own commands
and URCs; `a7672x_sockets.c` is the TCP/IP chapter (`NETOPEN`, the `CIP*`
links, DNS); `a7672x_ssl.c` is the SSL chapter (`CSSLCFG`, the `CCH*`
sessions). The engine, the standard commands, CMUX and PPP, SMS and the
network are the package's ([README](README.md)). The model has the modem,
network, link and SMS parts and its own: no GNSS.

## Attaching

The UART binding advertises the module's default rate, 115200 baud 8N1. On
fixture 1 the crossed pair is GP0/GP1 and the DUT's GP6 drives the
harness's GP6:

```python
import metalclaw
modem = metalclaw.attach("a7672x", "modem", uart=(0, 1), pwrkey=6)
modem.write_region("hosts", 0, b"vsh.pp.ua=192.0.2.80\nbroker.hivemq.com=192.0.2.18\n\0")
modem.write_region("file", 0, open("test_1k.bin", "rb").read())
modem.set(file_length=1024, latitude=31221946, longitude=121355565)
modem.powered, modem.pdp, modem.connections, modem.bytes_down
modem.reset()
modem.detach()
```

`pdp` is PDP context 1, `connections` counts links and sessions opened (and
the link's TCP connections), `registration` is the stat of `+CREG`,
`+CGREG` and `+CEREG` alike, `boot_ms` defaults to 5000 and `power_cycles`
counts boots.

The model's own part:

| name | type | access | unit | range | meaning |
| --- | --- | --- | --- | --- | --- |
| `latitude` | i32 | rw | 1e-6 deg | ±90e6 | the base-station fix `+CLBS` reports |
| `longitude` | i32 | rw | 1e-6 deg | ±180e6 | |
| `temperature` | i32 | rw | °C | -40 .. 125 | `+CPMUTEMP`, default 29 |
| `ready_urc` | bool | rw | | | the boot output ends with `APP RDY`, default false |

## Power and timing

| from | event | to |
| --- | --- | --- |
| off | PWRKEY low for 50 ms (Ton) | booting |
| booting or on | PWRKEY low for 2.5 s (Toff) | `POWERD DOWN`, off |
| booting | `boot_ms` later | `*ATREADY: 1`, `+CPIN: READY` (or `NOT INSERTED`, `SIM PIN`), `SMS DONE`, `PB DONE`, and `APP RDY` with `ready_urc`; on |
| on | `AT+CPOF`, `AT+CPOF=<0/1>` | `OK`, `POWERD DOWN`, off |
| on | `AT+CRESET`, `AT+CFUN=1,1`, `AT+CFUN=6` | `OK`, then the boot output at once |

The timings are the hardware design's (3.2.1, 3.2.2). Zephyr's 500 ms pulse
therefore boots an off modem and leaves a running one on. `SMS DONE` and
`PB DONE` come only with the SIM ready. No manual documents the boot
output; the four lines are what field units print, and neither driver
needs them.

A reset by command comes back at once, where a real module's UART is gone
for up to 10 s: TinyGSM's `restart()` sends `CFUN=0,0` straight after the
`CRESET` `OK` and allows 5 s after `CFUN=1,1` for the module to answer
`AT`.

`modem_cellular` waits 20 s after its power pulse unless it reads
`APP RDY`, which a real A7672X never sends; the model sends it only with
`ready_urc`, which cuts the wait to `boot_ms`.

Answers trail commands only where the manual has a reply after `OK` from a
network service: `+CNTP`, `+CLBS` and `+CUSD` come 100 ms after the `OK`.
The socket and SSL services reply (`+NETOPEN`, `+CIPOPEN`, `+CIPSEND`,
`+CIPCLOSE`, `+NETCLOSE`, `+CCHSTART`, `+CCHOPEN`, `+CCHSEND`,
`+CCHCLOSE`) right after the `OK`. Data and server closes arrive 10 ms
after the bytes that caused them, so a command's own reply always comes
first. Input waits while the output FIFO has less than 320 bytes free,
room for an `AT+CIPOPEN?` list; a URC waits for 80, room for a type-4
`+CLBS`.

In receive mode 1 `+CIPRXGET: 1,<link>` is sent when a link's buffer goes
from empty to not, never again until it has been emptied. A server close is
reported as `+IPCLOSE: <link>,1` only once the DUT has read every byte, and
frees the link.

| command | answer |
| --- | --- |
| `AT+CSSLCFG="<setting>",<ctx>,<value>` | `OK` for the manual's thirteen settings, contexts 0..9 |
| `AT+CSSLCFG=<ctx>` | `+CSSLCFG: <ctx>,<sslversion>,0,1,300,"","","","",<enableSNI>,0,0,0,0` |
| `AT+CCHSET=<report>[,<recv_mode>]`, `?` | kept; before `CCHSTART` only |
| `AT+CCHMODE=0`, `?` | `OK`; transparent mode is refused |
| `AT+CCHSTART[=1]` | attached: `OK`, `+CCHSTART: 0` and context 1 up; `ERROR`, `+CCHSTART: 17` not; `ERROR` when started |
| `AT+CCHSTOP[=1]` | `OK`, `+CCHSTOP: 0`; every session closes |
| `AT+CCHADDR` | `+CCHADDR: <ip>` |
| `AT+CCHSSLCFG=<session>,<ctx>`, `?` | kept until the session closes or fails to open |
| `AT+CCHOPEN=<session>,"<host>",<port>[,<1/2>[,<bind>]]` | `OK`, then `+CCHOPEN: <session>,<err>`: 0, 13 unknown host, 14 nothing listens, 17 context 1 down; `ERROR` before `CCHSTART`, on a busy session, for DTLS or a bad parameter |
| `AT+CCHOPEN?` | `+CCHOPEN: <session>,"<a.b.c.d>",<port>,<type>,` or `+CCHOPEN: <session>,"",,,` |
| `AT+CCHSEND=<session>,<len>` | `\r\n> `, exactly `len` (1..2048) bytes, `OK`, and with `report` 1 `+CCHSEND: <session>,0` |
| `AT+CCHRECV?` | `+CCHRECV: LEN,<cached 0>,<cached 1>` |
| `AT+CCHRECV=<session>[,<max>]` | `OK`, `+CCHRECV: DATA,<session>,<n>`, the bytes, `+CCHRECV: <session>,0`; a bare `ERROR` with nothing cached |
| `AT+CCHCLOSE=<session>` | `OK`, `+CCHCLOSE: <session>,0`; `ERROR` for a closed session |
| `AT+CCERTDOWN` | CME 4 |

In receive mode 1 `+CCHEVENT: <session>,RECV EVENT` is sent when a
session's cache goes from empty to not. A server close is reported as
`+CCH_PEER_CLOSED: <session>` once the cache is empty; the session stays the
DUT's to `CCHCLOSE`. The handshake is not modelled: a session is a plain
connection and the services on 443 answer as anywhere else.

Losing registration, CFUN 0 or 4, `CGATT=0` or `CGACT=0,1` with context 1
up ends everything at once, pending data discarded:
`+CIPEVENT: NETWORK CLOSED UNEXPECTEDLY` (with the service open), an
`+IPCLOSE: <link>,1` per link, a `+CCH_PEER_CLOSED: <session>` per session,
and `+CCH: CCH STOP` (with the SSL service started); a PPP link ends as
the package's link does. The socket service stays open until `NETCLOSE`.

A socket the PPP link's TCP holds is not a link or a session: it reads as
closed, and `CIPOPEN` or `CCHOPEN` on it is refused.

## The Zephyr driver this is built against

Zephyr v4.4.0, `drivers/modem/modem_cellular.c` with `simcom,a76xx`. Its
resume pulses `mdm-power-gpios` for 500 ms and waits 20 s, ended early
only by `APP RDY`. The init script on the raw UART: `AT` four times,
ignoring the answers; `ATE0`; `AT+CGNSSPWR=1` (`OK` or `ERROR`);
`AT+CFUN=4`; `AT+CMEE=1`; `AT+CREG=1`, `AT+CGREG=1`, `AT+CEREG=1`; the
three read forms, from which it takes the registration; `AT+CGSN` and
`AT+CGMM`, read by catch-all matches that take any line, so both answer
one bare line with echo off; `AT+CMUX=0,0,5,127`, whose answer it ignores.
Then the APN script (`AT+CGDCONT`), the dial script on DLCI 1
(`AT+CGACT=0,1`, `AT+CFUN=1`, `ATD*99***1#` waiting for `CONNECT`), the
periodic script on DLCI 2 (the three read forms every 2 s), and `AT+CPOF`
on the raw UART after the CMUX close-down to power off.
`cellular_get_signal()` sends `AT+CSQ` and `AT+CESQ`.

The quirks the model accommodates:

- No `+CGEV` lines: the driver reads them as registration changes.
- `AT+CGNSSPWR` is an `ERROR` the script accepts, never a later
  `+CGNSSPWR: READY!` that would land in a catch-all.
- `+CPIN: NOT READY` after `CFUN=4` and the registration URCs after
  `CFUN=1` go out after the `OK`, between script steps.

One behaviour of Zephyr's the cases record rather than avoid: after a long
loss of registration `net_if_down()` returns `-EAGAIN` after 3 s. The
model's LCP Terminate-Request, a few milliseconds behind the registration
URCs, ends the link before the driver has read the third of them (it counts
as deregistered only once `+CREG`, `+CGREG` and `+CEREG` all say so), so
Zephyr's PPP restarts LCP with the carrier still on; the driver's
carrier-off then leaves LCP in Starting and the phase at Establish, and
`ppp_lcp_lower_down()` waits `CONFIG_NET_L2_PPP_TIMEOUT` for a Dead phase
that never comes. The device suspend that follows works, and `NET UP`
brings the link back.

## TinyGSM

TinyGSM 0.12's `TinyGsmClientA7672X` (`TINY_GSM_MODEM_A7672X`) works
against the model, with its own bugs reproduced, not worked around:

- `restart()` gets its `CRESET`, `CFUN=0,0` and `CFUN=1,1` answered at
  once, and the module answers `AT` again before `init()` probes it.
- `init()` sends `ATV1` in a debug build and `ATV0` otherwise, calling
  them verbose error codes. `ATV0` switches the model to numeric result
  codes as it does a real module, so a non-debug build's later waits, which
  look for `OK\r\n`, time out; the examples here are debug builds.
- Every plain `write()` waits 10 s for a `+CCHSEND` the plain path never
  gets: the real reply is `+CIPSEND: <link>,<n>,<n>`.
- `CIPACK` after `CIPRXGET=4` reads 0 costs 1 s on an open link and 3 s on
  a closed one.
- `CCHRECV=` answers `OK` first, so TinyGSM idles 1 s at the end of every
  TLS read; `+CCH_PEER_CLOSED` follows the read that empties the cache.
- AllFunctions opens session 0 and sends on session 1: the send is `ERROR`
  and the TLS test receives nothing.
- `+CBC: 3.800V` parses as garbage (-15, -15, -10.00) and `+CPMUTEMP` as
  0.00; `+CNTP: 0` is the A76XX's success; `+CLBS` has latitude first, as
  TinyGSM expects; `AT+CNTPCID` is `ERROR` and ignored.
- `localIP()` after a TLS connect reads `+CCHADDR`, which has no comma.

## Not modelled

UDP links and the UDP forms of `CIPSEND`, the Ctrl-Z form of `CIPSEND`,
direct push (`CIPRXGET=0` and `CCHSET` receive mode 0: data waits for a read
without a URC), transparent modes (`CIPMODE=1`, `CCHMODE=1`, `ATO`, `+++`),
TCP servers, DTLS, the TLS handshake and certificates (`CCERTDOWN` and
friends), PDP contexts other than 1 (a PPP call on another `<cid>` holds
context 1), IPv6, GNSS, the HTTP(S), MQTT(S), FTP(S) and file-system
application commands, calls, incoming SMS and `+CMTI`, `CFUN=8`, the `+CREG`
location fields, `AT+IPR` reverting to `AT+IPREX` at boot (the rate survives
a boot), autobauding, flow control and sleep (`CSCLK` is only kept), command
concatenation with `;`, and the real module's 10 s of silence after a reset.
`AT+CPSI` is not answered. The clock in `time` does not run and `+CNTP` does
not set it.

## Tests

The model's host dialogues replay TinyGSM's A7672X transcript (restart,
`gprsConnect`, a 1 KiB HTTP download over `CIPRXGET` with CRC 0x6f50d767,
the same over `CCH*`, MQTT, `CLBS`, NTP, SMS, `CPOF`), `modem_cellular`'s
init script up to `AT+CMUX`, and a PPP call over CMUX that holds context 1
beside `CGACT`, under ASan and UBSan. The DUT image is
`test/dut/a7672x/`.

The image's `rp2.overlay` puts `uart0` on GP0/GP1 at 115200, removes the
console from it, and hangs a `simcom,a76xx` node aliased `modem` under it
with `mdm-power-gpios` on GP6, active low, its PWRKEY. The node is
`zephyr,deferred-init`: modem_cellular's init resumes the device at once,
which is a pulse on GP6 and a startup wait, and the rig flashes and pings
the DUT before a case attaches the model; `NET UP` runs the init. A GPIO
hog holds GP6 released from boot until the driver configures it: an
RP2350 pad resets with its pull-down on, and the harness's input has no
pull of its own. `rp2.conf` turns on
`CONFIG_MODEM_CELLULAR` with the APN `internet`, device PM, Zephyr's native
IPv4 stack over PPP (TCP, UDP, sockets, the DNS resolver fed by IPCP, no
IPv6, no Ethernet), the connection manager for L4 events, and
`CONFIG_MODEM_CMUX_WORK_BUFFER_SIZE_EXTRA=512`: the DLCI receive rings are
the CMUX work buffer size, and at the default two full UIH frames in one
UART batch overrun them. The image takes 122428 bytes of flash and 74376 of
RAM.

`NET UP` initialises the device (a PM resume after the first time), brings
the PPP interface up and waits for the connection manager's L4 connected,
which needs the address IPCP assigns; `NET DOWN` takes the interface down
and suspends the device, which closes CMUX and powers the part off as the
driver does it. `CELLULAR` reads the driver through the cellular API, and
`DNS`, `TCP`, `UDP`, `HTTP` and `SOCK` run on Zephyr's IP stack. The
reference is `test/rig/dut/README.md`.

```sh
just build-dut cellular/a7672x
METALCLAW_HARNESS_SERIAL=<serial> METALCLAW_ARM_TOOLCHAIN_DIR=<dir> \
METALCLAW_DUT_DEVICE=cellular/a7672x just test hardware
```

`test/cases/test_a7672x.py` subclasses the package's `PppModelCases`
(`common.py`). It resets the DUT, attaches the model at `uart=(0, 1)` and
`pwrkey=6`, sets `ready_urc` so `APP RDY` ends the driver's 20 s startup
wait, writes three names into `hosts` and a printable 1 KiB `file`, and
runs `NET UP`, then checks: the part was off and had never booted, and the pulse
brought it up once with CMUX and PPP up, PDP active and no unknown command;
the address and DNS server IPCP handed over; the modem info the init script
read (IMEI and model; the A76XX scripts read nothing else); the
registration the driver caches per technology (`+CREG`, `+CGREG` and
`+CEREG` all 1) and `-ENODATA` for 5G; `rssi` through `AT+CSQ` at 0, 17 and
31, unknown as `-EINVAL`, and RSRP and RSRQ through `AT+CESQ` (RSRQ -10
dB, RSRP one dB above the model's, as the driver reads the 27.007 index at
the top of its range); the driver's events, every periodic check over two
periods answered on DLCI 2; the APN fixed once dialled; no configurable
networks; DNS for every `hosts` name, a literal, and an unknown name
failing at once with `EAI_FAIL`, Zephyr's code for an answer without
records; TCP echo of 1 to 1000 bytes, three rounds each, intact by
CRC with the model's counters; the PPP and CMUX flag bytes through the
echo; UDP echo up to 256 bytes; an HTTP GET of the file intact with the
request line in `request`, a 404, and a refused port (`ECONNREFUSED`); no
frame with a bad FCS; a short loss of registration (the driver goes
dormant, PPP closes, and it redials without a power cycle); a long one
(three failed dials, the driver closes CMUX and powers down by itself,
`AT+CPOF` turning the part off, then `NET DOWN`, its `net_if_down()`
returning `-EAGAIN` as above, and `NET UP` restart it); and power off and
on through `NET DOWN` and `NET UP`, with no unknown command through all of
it. A case of its own clears `ready_urc` and finds the resume waits out the
20 s.
